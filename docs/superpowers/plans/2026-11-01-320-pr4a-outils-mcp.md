# PR4a (#320) — Outils MCP de lecture et d'édition du parcours « préparer mon cycle » : implementation plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** l'assistant peut lire le planning et la liste d'un cycle donné (`ancre`), voir l'accompagnement de chaque repas, marquer un repas en restes et chercher des recettes par attributs. Ce sont les briques de la skill « préparer mon cycle » (PR4b).

**Architecture:** les outils restent des fonctions de `lib/mcp/` injectables (client par jeton, RLS `mon_foyer()`), enregistrées dans `lib/mcp/serveur.ts`. Elles composent les services de l'UI (règle du jumeau). La résolution « date → cycle » de `generer_cycle` est extraite en helper unique, partagé par `generer_cycle`, `lire_planning` et `lire_liste_courses`. Aucune migration.

**Tech Stack:** Next.js 16, Supabase, `@modelcontextprotocol/server` + `mcp-handler`, zod, Vitest (`npm run test:run`), Playwright e2e (staging).

**Spec:** `SPECS_FONCTIONNELLES.md` RG-85 (outils du parcours), RG-22 (restes), RG-73→79 (contrats MCP) ; issue #320, découpage révisé, « PR4a ».

## Global Constraints

- Client par jeton seulement (`creerClientParJeton`), jamais `clientParDefaut()` ni `service_role` (RG-71, `.claude/rules/mcp.md`).
- Date du jour serveur = `aujourdhuiParis()`. Les fonctions de `lib/mcp/` reçoivent `aujourdhui` en paramètre.
- Un repas = `date` (AAAA-MM-JJ) + `creneau` (`midi` | `soir`), plage −12/+6 semaines (`semaineDansPlage`).
- `ancre` = **une date quelconque du cycle visé**, AAAA-MM-JJ, résolue **exactement comme `generer_cycle`** : `validerDate`, puis `ancreCourante(depuisISO(ancre), jourCourses)`, puis le contrôle de plage avec le message `CYCLE_HORS_PLAGE`.
- Erreurs attendues = `ErreurOutil`, message français qui dit quoi faire ensuite. Une ambiguïté n'est pas une erreur.
- Toute évolution de contrat se répercute dans la `description` de l'outil (`lib/mcp/serveur.ts`), que lit l'assistant.
- Noms d'outils et identifiants en français ; commentaires qui citent RG-85 / RG-22 / #320.
- Écritures par les mêmes RPC que l'UI (`sauvegarder_slots` via `ecrireCreneau`), pour que le temps réel et l'alerte US-21 suivent (RG-79).

## Review Focus

1. **`semaine` et `ancre` passés ensemble à `lire_planning`** : refus explicite (« choisis l'un ou l'autre »), jamais l'un ignoré en silence. → test Task 1.
2. **`ancre` mal formée, impossible (`2026-02-30`) ou hors plage** sur `lire_planning` / `lire_liste_courses` : même message que `generer_cycle`, rien n'est lu. → tests Task 1.
3. **`marquer_restes` sur un créneau vide ou désactivé** : `ErreurOutil` « Aucun repas prévu… », rien n'est écrit. **Et le repas voisin du même jour n'est jamais réécrit.** → tests Task 2.
4. **`chercher_recettes` ne renvoie jamais une recette masquée**, ni une recette d'un autre foyer (RLS). Le résultat varie d'un appel à l'autre (tirage), sinon l'assistant reproposerait toujours les mêmes 10 recettes. → tests Task 3.
5. **Démarquer (`restes: false`) restitue la recette d'origine** (RG-22, la recette sous-jacente est conservée). → test Task 2.

### Task 3 : `chercher_recettes`

**Files:**
- Create: `lib/mcp/recherche-recettes.ts`
- Modify: `lib/mcp/ecriture-planning.ts` (`homonymeDuFoyer` utilise `idsRecettesDuFoyer`), `lib/mcp/serveur.ts`
- Test: `lib/mcp/recherche-recettes.test.ts`, `app/api/mcp/route.test.ts`

**Interfaces:**
- Produces:

```ts
export type FiltresRecettes = {
  texte?: string
  temps_preparation?: TempsPreparation   // égalité stricte
  vegetarien?: boolean
  accompagnement?: Accompagnement        // "feculents" | "legumes"
  saison?: Saison                        // estDeSaison (sans saison déclarée = toute l'année)
}
export type RecetteTrouveeMcp = {
  nom: string
  temps_preparation: TempsPreparation
  vegetarien: boolean
  accompagnement: Accompagnement | null
  saisons: Saison[]                      // [] = toute l'année
  origine: "foyer" | "catalogue"
}
export async function idsRecettesDuFoyer(supabase: ClientSupabase): Promise<Set<string>>  // extrait de homonymeDuFoyer
export async function chercherRecettes(
  supabase: ClientSupabase,
  filtres: FiltresRecettes,
  aleatoire: () => number = Math.random
): Promise<{ recettes: RecetteTrouveeMcp[]; total: number }>
```

- Comportement :
  - recettes de `chargerRecettes(supabase)` (masquées déjà exclues, RLS foyer) ; tous les filtres présents s'appliquent (ET) ; `texte` par `filtrerRecettes` (contient, casse et accents ignorés) ;
  - `total` = nombre de correspondances ; au-delà de `RECETTES_MAX = 10`, **tirage** de 10 sans remise avec `aleatoire`, pour que des appels successifs varient ; le résultat est trié par nom (`localeCompare(…, "fr")`) ;
  - aucun filtre → tirage parmi toutes les recettes visibles ;
  - aucune correspondance → `{ recettes: [], total: 0 }`, pas une erreur.
- Outil `chercher_recettes` dans `enregistrerOutilsLecture` (lecture seule). Schéma zod avec les cinq filtres optionnels (`SAISONS` déjà importé). Description : « Cherche des recettes par attributs, sans rien modifier : `temps_preparation`, `vegetarien`, `accompagnement`, `saison`, `texte` (dans le nom). Renvoie 10 recettes au plus, tirées au hasard parmi les correspondances (`total`), avec leurs attributs et leur origine (recette du foyer ou du catalogue). Pour en mettre une au planning, appelle remplacer_repas avec son nom exact. »

  - « aucune correspondance → recettes vide, total 0 ».
