# #308 PR3 — Exécuteur Chronodrive (MCP maison + skill Hermes) : plan d'implémentation

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** Le clic « Constituer mon panier Chronodrive » remplit réellement le panier de ton compte Chronodrive. Hermes, sur le NAS, prend la demande, mappe la liste avec un MCP Chronodrive maison, ajoute les articles en confiance haute, coche chaque article ajouté dans OMQ, puis rapporte à OMQ et sur Telegram.

**Architecture:**
- `integrations/chronodrive-mcp/` (même dépôt, jamais déployé par Vercel ni testé par la CI de l'app) contient :
  - un client HTTP Chronodrive en TypeScript, exécuté tel quel par Node 26 (type stripping, sans build) ;
  - un cache `node:sqlite` des correspondances ;
  - un serveur MCP stdio par lot ;
  - la skill Hermes `panier-chronodrive`.
- OMQ ne change pas : le socle (PR1) et la carte (PR2) sont en prod.
- Le déploiement sur le NAS et les mesures sur le vrai compte sont des tâches **avec Arnaud** (voir Global Constraints).

**Tech Stack:** Node 26 (conteneur `hermes`) et Node 24 en local, `fetch` / `crypto` / `node:sqlite` / `node:test` natifs, `@modelcontextprotocol/sdk` 1.32.2 + `zod` 4.6.7 (versions du spike), Hermes Agent v0.21.5 (MCP stdio, skills `SKILL.md`, routes webhook dynamiques), conteneur `tailscale` (Funnel).

**Spec:** `SPECS_FONCTIONNELLES.md` US-53, RG-80→84 ; `ADR.md` ADR-12 ; `docs/etudes/chronodrive.md`, « Résultats du spike » et « Protocole relevé » ; issue #308, « Réserves du spike à lever » et « Découpage et décisions ». Règle : `.claude/rules/chronodrive.md`. PoC de référence : `integrations/chronodrive-mcp/spike/`. Reconnaissance du NAS (2026-10-31) : voir « Faits Hermes » ci-dessous.

## Global Constraints

- **RG-80 / ADR-12** : les identifiants Chronodrive ne quittent jamais le NAS (`/opt/data/chronodrive.env`, mode `600`). Rien dans Git, rien dans `config.yaml`, rien dans OMQ. Le code ne logge jamais un mot de passe, un jeton ni un cookie.
- **RG-82** : le MCP n'expose **aucun** outil de commande, de créneau ou de paiement, et aucun outil de retrait.
- **Le code n'appelle que les endpoints du « Protocole relevé »** (`docs/etudes/chronodrive.md`) : login, autorisation, jeton, `customers/me`, `customers/me/carts`, `carts/{id}`, `carts/{id}/items` (POST seulement), `favourite-products`, `products`, `sites`. Les constantes publiques (`x-api-key` par service, `CLIENT_ID`) sont lues dans le HTML de `https://www.chronodrive.com`, jamais recopiées en dur.
- **Une clé `x-api-key` par service**, la route décide : `customers/me/carts` attend `CUSTOMERS`, pas `CARTS`. Un 401 « API Key is not valid » est une erreur de clé et ne déclenche pas de reconnexion.
- **Pas de refresh token** : sur un jeton expiré (`expires_in` 7 200 s, avec une marge de 60 s), ou sur un 401 d'authentification en cours de run, on refait le login complet, **une seule fois** par appel, puis l'appel est rejoué une fois.
- **Panier courant relu à chaque run**, via `customers/me/carts` et sans cache de `panierId`.
- **Un ajout se confirme en comparant la quantité du produit dans le panier avant et après** (RG-83), jamais au `returnType`, puisque `NO_STOCK_AFTER` ajoute quand même le produit.
- **Disponibilité** : un produit n'est proposé ni ajouté que si `isEligible !== false`, que le stock est positif (`remainingStock` ou `stock`, selon le champ présent) et que la quantité demandée est ≤ `maxCartQuantity` quand il existe. Sinon il est marqué `disponible: false` avec la raison.
- **Favoris d'abord** : `favourite-products`, paginé (`page` dès 1, `size=50`, tant que `page.hasNext`), chargé une seule fois par processus et mis en mémoire pour la durée du run.
- **Cache des correspondances** : `terme normalisé → productId` (minuscules, sans accents, espaces réduits), écrit **seulement** après un ajout confirmé. Une entrée dont le produit n'est plus disponible est ignorée et supprimée. Base : `/opt/data/chronodrive-correspondances.sqlite` (chemin surchargeable par `CHRONODRIVE_CACHE`).
- **Lecture seule par défaut** : `ajouter_au_panier` est refusé sans aucun appel API sauf si `CHRONODRIVE_LECTURE_SEULE` vaut exactement `'0'` (mesures et déploiement à blanc sans rien poser ; écriture sur un `'0'` explicite seulement).
- **Code exécuté par Node sans build** : TypeScript à syntaxe effaçable seulement (pas d'`enum`, de `namespace` ni de paramètres de propriété), imports relatifs avec l'extension `.ts`, `"type": "module"`. Il tourne sur Node 24 (local) et 26 (NAS).
- **Hors de l'app** : `integrations/` est exclu du `tsconfig.json` racine, de l'ESLint racine, de Vitest, et ajouté aux `paths-ignore` de la CI. Il a son propre `package.json` et son propre `tsconfig.json` (`tsc --noEmit` local), et ses tests passent par `node --test`.
- **Consignes de la skill** (RG-82, préférences d'Arnaud) :
  - acheter **explicitement** les articles « à vérifier au placard » non cochés ;
  - une différence de marque, de format ou de label n'est pas une ambiguïté, seule la nature du produit en est une ;
  - à défaut de favori, préférer les **marques nationales** aux marques distributeur ;
  - cocher chaque article dans OMQ (`cocher_article`) **juste après** son ajout confirmé ;
  - rapporter une seule fois (`rapporter_panier`), avec des listes vides si rien n'a été fait ;
  - ne jamais réessayer un rapport refusé.
- **Opérations sur le NAS et en prod = avec Arnaud.**
  - Avant de toucher `config.yaml`, le sauvegarder (`config.yaml.bak-avant-308-<étape>`).
  - **Prévenir Arnaud avant tout redémarrage** de la gateway, qui porte Telegram, WhatsApp, Home Assistant et le cron. Préférer `s6-svc -t /run/service/gateway-default` à `docker restart hermes`.
  - Les identifiants du vrai compte sont posés **par Arnaud lui-même** dans `chronodrive.env`.
  - L'enregistrement de l'exécuteur en prod (SQL sur `gabyhlcwahzquolwxmgd`) se fait sur son accord explicite.
- Commits `type: description (#308)` avec le trailer de session ; `CHANGELOG.md` et `.claude/rules/chronodrive.md` à jour dans la PR.

- **Tailscale Funnel** : aucune configuration active. Le port 10000 est à rouvrir (`tailscale funnel --bg --https=10000 --set-path /webhooks/<route> http://127.0.0.1:8644/webhooks/<route>`), et 443 et 8443 sont pris.
- **Gateway** : s6-overlay, service `gateway-default` (`hermes gateway run --replace`), déjà redémarrée chaque jour vers 04 h 16.
- **Runtime** : Node v26.5.1, npm 11.17.0, `node:sqlite` disponible.

## Review Focus

1. **Jeton expiré en plein run, entre deux lots.** On attend une reconnexion transparente, une seule fois, et l'appel rejoué. Une boucle de login, ou l'abandon du run, serait un défaut. Test : Task 1, `401 jeton → login complet puis rejeu, une seule fois` et `401 clé API → pas de login`.
2. **Article déjà présent dans le panier**, ajouté à la main avant la demande ou par un run interrompu entre l'ajout et la coche. Côté code, l'ajout est confirmé par l'écart de quantité, pas par la simple présence (Task 2, `ajout confirmé par écart de quantité, produit déjà présent` et `NO_STOCK_AFTER avec écart → confirmé`), et la relecture finale est retentée une fois (`relecture finale en échec une fois : retentée`). Côté skill, au début du run (`lire_panier`), un article « haute » dont le produit choisi est déjà au panier passe « à choisir » (« déjà au panier, vérifie la quantité »), sans ajout ni coche : une relance ne le double jamais (RG-83). Un « ajout envoyé mais panier non relu » est un échec technique, ses lignes sont rapportées « peut-être ajoutées, à vérifier dans le panier ».
3. **Produit en rupture**, ou quantité au-delà de `maxCartQuantity`. Il n'est jamais ajouté et apparaît en `disponible: false` avec sa raison. Test : Task 2, `indisponible jamais ajouté` et Task 4, `chercher_produits marque l'indisponible`.
4. **Panier changé après une commande validée.** L'identifiant du panier est relu au début de chaque run. Test : Task 2, `panier courant relu à chaque appel de session`.
5. **Mot de passe ou jeton dans un log ou un message d'erreur MCP.** Les erreurs sont réécrites sans valeur sensible. Test : Task 1, `erreur de login sans secret dans le message`.

### Task 4 : serveur MCP stdio par lot

**Files:** Create `integrations/chronodrive-mcp/src/outils.ts` (logique des outils, testable), `src/mcp.ts` (enregistrement + transport stdio), `test/outils.test.ts`.

**Interfaces:**
- Consumes : Tasks 1-3.
- Produces : les outils (noms français, descriptions écrites pour le LLM) :
  - `chercher_produits({ termes: string[] (1..40) })` → par terme, `{ terme, cache: Produit | null, favoris: Produit[] (≤ 5), recherche: Produit[] (≤ 8) }`. Le cache passe d'abord et n'est retenu que si le produit est encore disponible, sinon `oublier`. Viennent ensuite les favoris qui correspondent au terme (normalisation + inclusion des mots), puis la recherche, lancée **seulement** si aucun favori ne correspond. Les indisponibles sont gardés et marqués.
  - `ajouter_au_panier({ lignes: { terme: string; productId: string; quantite: number }[] (1..20) })` → `ResultatAjout[]` (plus `terme`). Les lignes confirmées sont mémorisées dans le cache. Refus sans appel API sauf si `CHRONODRIVE_LECTURE_SEULE` vaut `'0'`.
  - `lire_panier()` → `{ lignes: { produit: Produit; quantite: number }[] }`.
  - `correspondances_connues({ termes })` et `memoriser_correspondances({ entrees })` : exposition directe du cache, pour corriger une correspondance à la main.
  - Aucun outil de retrait, de commande, de créneau ou de paiement.
  - Toute erreur devient `isError` avec un message français, sans secret.
