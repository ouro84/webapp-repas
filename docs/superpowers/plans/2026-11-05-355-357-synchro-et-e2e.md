# Robustesse de la synchro temps réel (#355) et e2e robustes aux gels de staging (#357) Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** Fermer les fragilités restantes de `lib/sync.ts` (alertes perdues, canal rouvert hors `/planning`, éditions locales écrasées, course écriture/régénération) et rendre la CI e2e fiable face aux gels du Supabase de staging.

**Architecture:** La fusion « éditions locales en attente × changement distant » est une fonction pure (`lib/planning-fusion.ts`) branchée dans la relecture US-21 grâce à un instantané « dernier planning confirmé » persistant. Les autres points sont des gardes ciblées dans `lib/sync.ts` (rejeu d'event, abonnement autorisé, flush avant génération). Côté e2e : tests qui amorcent leur état en base au lieu de générer, attentes sur le résultat (toast) plutôt que sur un délai, script `e2e-staging` sans shell, jobs CI e2e sérialisés.

**Tech Stack:** Next.js 16, React, Supabase Realtime, Vitest, Playwright (staging), GitHub Actions.

**Spec:** issues #355 et #357 (`gh issue view 355`, `gh issue view 357`) + décisions d'Arnaud du 2026-11-05 (ci-dessous).

## Global Constraints

- Décision point 5 (#355) : quand une relecture US-21 survient alors que des éditions locales ne sont pas encore poussées, **on rejoue les éditions locales sur les créneaux que le distant n'a pas touchés ; sur un même créneau, le distant gagne** (l'alerte le signale). Les éditions rejouées repartent en push.
- Décision point 3 (#355) : **pas de migration** ; la limite « deux écritures dans la même microseconde » est documentée dans `.claude/rules/sync-planning.md`.
- Décision point 4 (#355) : **avant de régénérer le cycle, on attend la fin des envois en attente** de la semaine (`attendreSync`).
- Décision CI (#357) : **les jobs e2e `partage` et `jetable` sont sérialisés** (`partage` d'abord).
- Point 6 (#355, alerte cycle non levée quand l'autre membre commite avant la relecture de `rafraichirCycleGenere`) : pas de perte de donnée ; **documenté, non corrigé** (ruling contrôleur, à valider à la relecture du plan).
- Créneau = (jour, `typeRepas`) ; son contenu comparé = id de recette (ou absence), personnes (avec le défaut `PERSONNES_DEFAUT` = 2 quand absent), drapeau restes.
- Tout en français, `.claude/rules/` mis à jour dans le même commit que le code, entrée `CHANGELOG.md` `[Unreleased]` pour tout changement visible. Jamais `npm run test:e2e` en local ; e2e une spec à la fois.
- Consigne d'Arnaud : aucun e2e connu rouge ou flaky ne part en CI (mesurer sans retry avant de pousser).

## Review Focus

1. **Éditions locales sur un créneau supprimé/vidé à distance** (créneau désactivé, recette retirée) : la fusion ne doit pas ressusciter un créneau que le distant a vidé — c'est un changement distant, le distant gagne.
2. **Rafales** : plusieurs events distants pendant une relecture + édition locale en attente → un seul rejeu final, aucun push perdu, `planning_dirty` cohérent.
3. **Changement de foyer / déconnexion** : l'instantané confirmé est purgé par `reinitialiserCacheFoyer` (sinon fusion contre l'ancien foyer).
4. **Hors-ligne au moment de régénérer le cycle** : `attendreSync` renvoie faux → la génération ne part pas et l'utilisateur voit un message, pas un échec muet.
5. **Script e2e sous Windows** : `-g "a b|c"` et les arguments avec espaces/accents arrivent intacts à Playwright.
