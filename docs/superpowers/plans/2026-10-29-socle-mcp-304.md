# Socle serveur MCP (#304) — plan d'implémentation

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal :** rendre la génération, les lectures du cycle et l'écriture d'un cycle appelables côté serveur **en tant qu'un utilisateur** (client Supabase injecté, RLS `mon_foyer()`), sans aucun changement visible côté web.

**Architecture :** la logique de génération quitte la route pour `lib/generation.ts` (la route devient un adaptateur HTTP mince). Les lectures de `lib/persistance.ts`, `lib/foyer.ts` et `lib/reglages-data.ts` prennent un client optionnel (défaut : client navigateur). Une RPC atomique `sauvegarder_cycle` remplace la séquence client « N × `sauvegarder_slots` + purge des coches » ; le web l'utilise dès cette PR (règle du jumeau). Un service `lib/liste-courses-cycle.ts` assemble la liste du cycle à partir d'un assembleur pur partagé avec `/courses`. Une fabrique `creerClientParJeton` prépare le client « par jeton » de #305.

**Tech Stack :** Next.js 16 (route handler), Supabase (`@supabase/supabase-js` 2.x, PL/pgSQL), Vitest 4 (jsdom ; `node` pour la route), Playwright contre staging.

**Spec :** issue #304 (épopée #302) ; `SPECS_FONCTIONNELLES.md` US-50→52, RG-71→79 (surtout RG-71, RG-73, RG-74, RG-78, RG-79) ; `ADR.md` ADR-11. Cadrage arbitré en grilling le 2026-10-29 : on ne rouvre pas le design.

## Global Constraints

- Code, identifiants, commentaires et messages d'erreur **en français** ; les commentaires citent les `RG-xx` / `US-xx` (RG-13, RG-71, RG-73, RG-74, RG-79, US-21…).
- **Jamais de `service_role`** hors `lib/supabase/admin.ts` (RG-71) : la fabrique par jeton n'utilise que `NEXT_PUBLIC_SUPABASE_URL` + `NEXT_PUBLIC_SUPABASE_ANON_KEY`.
- **Comportement web strictement inchangé** : mêmes corps de réponse JSON de `POST /api/planning/generer`, mêmes messages d'erreur, mêmes codes HTTP, même temps réel, même alerte US-21.
- RPC : `SECURITY DEFINER`, `set search_path = public`, foyer = `mon_foyer()` (jamais fourni par le client), bump de `planning.version`, `revoke … from public` **et** `from anon`, `grant … to authenticated`.
- Migration nommée `supabase/migrations/20261029120000_sauvegarder_cycle.sql`.
- TypeScript strict : on corrige les erreurs de type, on ne les contourne pas.
- **Jamais `npm run test:e2e` en local** (`.env.local` = prod). E2E uniquement via `npm run test:e2e:staging`.
- **Aucune action sur la prod** (migration, merge) sans validation explicite de l'utilisateur, ordre exact des opérations présenté avant (Task 7).
- Hors périmètre : #305, #306, #303 (pas d'OAuth, pas de route `/api/mcp`, pas d'outil MCP, pas de garde « cycle existant » de RG-74, qui relève de `generer_cycle` en #306).
- Flaky connus sur `main`, à ne pas confondre avec une régression : `planning-edition` « annuler une régénération restaure aussi les coches » et `planning.spec` « sélection manuelle conserve les coches » (RG-15/RG-12).

## Review Focus

1. **Cycle de 14 j qui touche 3 semaines ISO** (ancre un dimanche) : la RPC doit boucler sur N semaines, pas sur 2. Testé en Task 4 (génération) et Task 3 (smoke SQL à 2 semaines + test client).
2. **Échec au milieu de l'écriture** (2ᵉ semaine invalide) : rien ne doit être écrit, et les coches doivent rester intactes. Testé par le smoke SQL « atomicité » (Task 3) et le test `sync` « échec RPC → coches locales intactes ».
3. **Appel avec une liste de semaines vide ou une ancre mal formée** (cas du futur appel MCP) : la RPC refuse avec un message explicite au lieu de purger les coches pour rien. Testé par le smoke SQL (Task 3).
4. **Client par jeton sans jeton ou sans variables d'environnement** : erreur explicite, jamais un client anonyme silencieux. Testé en Task 1.
5. **Corps vide `{}` un samedi** : la semaine par défaut doit rester la semaine suivante (`semaineParDefaut`), comme aujourd'hui. Testé en Task 4.

Algorithme (non déterminé par la signature) : chaque `from(table)` renvoie un builder chaînable qui enregistre chaque appel de méthode, et qui se résout (par `await`, `maybeSingle()` ou `single()`) sur la réponse configurée pour la table ; la réponse peut être une fonction de l'appel enregistré, ce qui permet de répondre selon un filtre `eq("semaine", …)`.

```ts
export type ReponseMock = { data: unknown; error: { message: string } | null; count?: number | null }
export type AppelTable = { table: string; ops: Array<[string, ...unknown[]]> }
export type AppelRpc = { nom: string; args: unknown }
export type ConfigMock = {
  tables?: Record<string, ReponseMock | ((appel: AppelTable) => ReponseMock)>
  rpc?: Record<string, ReponseMock | ((args: unknown) => ReponseMock)>
}

export function creerSupabaseMock(config: ConfigMock = {}) {
  const appels: AppelTable[] = []
  const rpcs: AppelRpc[] = []
  const repondre = (appel: AppelTable): ReponseMock => {
    const r = config.tables?.[appel.table] ?? { data: null, error: null }
    return typeof r === "function" ? r(appel) : r
  }
  const client = {
    from(table: string) {
      const appel: AppelTable = { table, ops: [] }
      appels.push(appel)
      const builder: Record<string, unknown> = new Proxy({}, {
        get(_cible, prop) {
          if (prop === "then") {
            return (ok: (v: ReponseMock) => unknown, ko: (e: unknown) => unknown) =>
              Promise.resolve(repondre(appel)).then(ok, ko)
          }
          return (...args: unknown[]) => {
            appel.ops.push([String(prop), ...args])
            return prop === "maybeSingle" || prop === "single"
              ? Promise.resolve(repondre(appel))
              : builder
          }
        },
      })
      return builder
    },
    rpc(nom: string, args: unknown) {
      rpcs.push({ nom, args })
      const r = config.rpc?.[nom] ?? { data: null, error: null }
      return Promise.resolve(typeof r === "function" ? r(args) : r)
    },
  }
  return { client: client as unknown as ClientSupabase, appels, rpcs }
}
```

  `filtre(appel, "eq", "semaine")` renvoie la valeur du premier `["eq", "semaine", v]` de `appel.ops` (ou `undefined`).

```sql
-- « Générer mon cycle » atomique (#304, socle du serveur MCP #302, RG-74/RG-79).
-- Remplace la séquence client « sauvegarder_slots par semaine ISO, puis purge
-- des coches » (N appels non atomiques) : écrit les jours du cycle sur TOUTES
-- les semaines ISO touchées ET purge les coches du cycle (RG-13) dans UNE
-- transaction. Utilisée par le web ET par le serveur MCP (règle du jumeau).
-- Même contrat que sauvegarder_slots par semaine : upsert des seuls
-- (jour, type_repas) fournis, foyer = mon_foyer(), bump de `version` (US-21),
-- updated_at posé par le trigger serveur (#104), renvoyé par semaine.
create or replace function sauvegarder_cycle(p_ancre text, p_semaines jsonb)
returns jsonb
language plpgsql
security definer
set search_path = public
as $$
declare
  v_foyer uuid := mon_foyer();
  v_semaine jsonb;
  v_planning_id uuid;
  v_updated timestamptz;
  v_resultat jsonb := '{}'::jsonb;
begin
  if v_foyer is null then
    raise exception 'Aucun foyer rattaché à l''utilisateur courant';
  end if;
  if p_ancre is null or p_ancre !~ '^\d{4}-\d{2}-\d{2}$' then
    raise exception 'Ancre de cycle invalide : %', p_ancre;
  end if;
  if p_semaines is null or jsonb_typeof(p_semaines) <> 'array'
     or jsonb_array_length(p_semaines) = 0 then
    raise exception 'Aucune semaine à sauvegarder pour le cycle %', p_ancre;
  end if;

  for v_semaine in select value from jsonb_array_elements(p_semaines) loop
    if coalesce(v_semaine->>'semaine', '') !~ '^\d{4}-W\d{2}$' then
      raise exception 'Semaine invalide : %', v_semaine->>'semaine';
    end if;

    insert into planning (foyer_id, semaine)
      values (v_foyer, v_semaine->>'semaine')
      on conflict (foyer_id, semaine)
        do update set version = planning.version + 1
      returning id, updated_at into v_planning_id, v_updated;

    delete from planning_slot ps
    using jsonb_array_elements(v_semaine->'slots') as s
    where ps.planning_id = v_planning_id
      and ps.jour = s->>'jour'
      and ps.type_repas = s->>'type_repas';

    insert into planning_slot (planning_id, recette_id, jour, type_repas, personnes, restes)
    select
      v_planning_id,
      (s->>'recette_id')::uuid,
      s->>'jour',
      s->>'type_repas',
      coalesce((s->>'personnes')::int, 2),
      coalesce((s->>'restes')::boolean, false)
    from jsonb_array_elements(v_semaine->'slots') as s;

    v_resultat := v_resultat || jsonb_build_object(v_semaine->>'semaine', v_updated);
  end loop;

  -- RG-13 : une régénération réinitialise les coches du cycle, dans la même
  -- transaction (plus de cycle écrit sans purge, ni de purge sans cycle).
  delete from etat_courses_article
  where foyer_id = v_foyer and ancre = p_ancre::date;

  return v_resultat;
end;
$$;

revoke execute on function sauvegarder_cycle(text, jsonb) from public;
revoke execute on function sauvegarder_cycle(text, jsonb) from anon;
grant execute on function sauvegarder_cycle(text, jsonb) to authenticated;
```
