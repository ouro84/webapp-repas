## Défaut : « lait » ajouté en lasagnes

L'article OMQ « lait » a été ajouté au panier sous la forme « Feuilles de lasagnes aux oeufs N°199 » (BARILLA, id 1697). C'est un achat faux.

Cause :

1. `chercher_produits` avait bien renvoyé, pour « lait », le favori d'Arnaud « Lait demi-écrémé 1,5% M.G UHT bio » (LACTEL, id 146939).
2. L'id 1697 figurait parmi les favoris du terme « œufs », parce que son libellé contient « aux oeufs ».
3. Le LLM a recopié l'id 1697 sur la ligne « lait » de `ajouter_au_panier`.
4. La garde de l'outil vérifiait seulement que le produit avait été **vu** dans les 30 dernières minutes, pas qu'il avait été **proposé pour ce terme**. L'ajout a été confirmé par l'écart de quantité, et l'article a été coché dans OMQ.

Correctif (branche `feat/308-executeur`) :

- **Garde par terme** : `ajouter_au_panier` refuse sans envoi une ligne dont le produit n'a pas été proposé par `chercher_produits` pour son terme (ou pour sa reformulation, passée en `terme_recherche`) depuis moins de 30 min. Erreur : « produit non proposé pour cet article : relance chercher_produits pour ce terme ».
- **Favoris plus stricts** : un mot du terme ne compte plus quand il ne figure dans le libellé qu'après une préposition de complément (« au », « aux », « à », « à la », « à l' », « de », « du », « des », « d' », « en ») ; la marque ne compte plus. « œufs » ne propose plus les lasagnes « aux oeufs », « lait » ne propose plus d'œufs en chocolat « au lait ».
- **Skill** : copier l'`id` depuis le bloc de résultat du terme de l'article et vérifier son `libelle` ; passer `terme_recherche` après une reformulation ; classer le nouveau refus « à choisir » sans relance.
- **Reformulation encadrée** : `terme_recherche` n'est accepté que si l'article a été cherché et si la reformulation l'a été pour la première fois dans un appel postérieur. Sans cela, `{terme: "lait", terme_recherche: "œufs"}` contournait la garde.

Le correctif ne répare pas le **cache des correspondances** : l'ajout faux a été confirmé, donc le cache du NAS retient « lait » → lasagnes (id 1697). Au run suivant, `chercher_produits(["lait"])` renverrait les lasagnes en `cache`, et la garde l'accepterait (proposé pour « lait »). Même risque pour « lentilles (boîte) » (doute ci-dessous).

## Avant le run #2 : purger le cache (obligatoire)

Clés normalisées (`normaliserTerme`) : `lait` et `lentilles (boite)`. Sur le NAS, dans le conteneur `hermes`, entre deux runs :

```sh
node --input-type=module <<'JS'
import { DatabaseSync } from "node:sqlite";
const base = new DatabaseSync("/opt/data/chronodrive-correspondances.sqlite");
const cles = ["lait", "lentilles (boite)"];
console.log(base.prepare("delete from correspondance where terme in (?, ?)").run(...cles));
// Vérification : aucune ligne restante pour ces clés, puis relecture du cache entier.
console.log(base.prepare("select terme, product_id, libelle from correspondance where terme in (?, ?)").all(...cles));
console.table(base.prepare("select terme, product_id, libelle from correspondance order by terme").all());
base.close();
JS
```

SQL équivalent : `delete from correspondance where terme in ('lait', 'lentilles (boite)');`. Relire ensuite le cache entier à la recherche d'une autre correspondance fausse. Si les lentilles en boîte sont confirmées justes, on peut ne purger que `lait`.

Le critère « 0 faux » (RG-82) **n'est pas tenu** par ce run.
